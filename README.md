# MAX × GREEN-API Chat

Тестовое задание на позицию фронтенд-разработчика React: минимальный интерфейс для обмена текстовыми сообщениями в MAX через GREEN-API. Проект готов к добавлению собственных учётных данных. Бэкенд и отдельная база данных для задания не требуются.

[Пошаговая ручная проверка](MANUAL_TESTING.md) · [Соответствие требованиям ТЗ](REQUIREMENTS.md)

## Быстрый запуск

Нужны Node.js **22.14+** (либо совместимая версия: 20.19+ / 22.12+) и npm.

```sh
cd max-green-chat
npm install
npm run dev
```

Открой **http://127.0.0.1:5173**. В форме подключения заполни:

| Поле | Откуда взять |
| --- | --- |
| `apiUrl` | Точный адрес API своего MAX-инстанса в личном кабинете GREEN-API, например `https://3100.api.green-api.com`. У разных инстансов адрес может отличаться. |
| `idInstance` | Номер MAX-инстанса |
| `apiTokenInstance` | Токен доступа к этому инстансу |

В код ничего вставлять не нужно. Кнопка **«Открыть демо без токена»** позволяет посмотреть интерфейс, переключать чаты и локально добавлять сообщения без регистрации и сетевых запросов к GREEN-API. Собеседники и сообщения в демо — примеры; ответы автоматически не имитируются.

Необязательно: скопируй `.env.example` в `.env.local` и укажи `VITE_GREEN_API_URL`, чтобы предзаполнить поле `apiUrl`. После изменения перезапусти Vite. **Не добавляй токен в переменные `VITE_*`: их значения попадают в публичную сборку.**

## Подготовка GREEN-API

1. Создай инстанс именно для **MAX** в [личном кабинете GREEN-API](https://console.green-api.com/).
2. Авторизуй свой MAX-аккаунт. Для подключения приложение ожидает `stateInstance: authorized`. Авторизация по QR/коду выполняется в кабинете сервиса и не входит в этот минимальный интерфейс.
3. Для получения через HTTP API оставь `webhookUrl` пустым и включи `incomingWebhook: yes`.
4. Необязательно включи `outgoingWebhook: yes`, `outgoingMessageWebhook: yes`, `outgoingAPIMessageWebhook: yes`, чтобы получать статусы исходящих сообщений, и `stateWebhook: yes`, чтобы получать изменения состояния инстанса. Настройки меняются в кабинете; приложение не перезаписывает их автоматически.
5. После изменения настроек дай сервису время применить их. Не запускай другой потребитель очереди этого же инстанса одновременно: уведомления распределяются между потребителями.
6. Войди в приложение, нажми **«+»**, введи телефон получателя с кодом страны, например `+7 999 123-45-67`, и отправь текст. Ответь с аккаунта получателя в MAX — ответ появится в чате.

По документации `CheckAccount` принимает 11–12 цифр. Пробелы, скобки и дефисы удаляются; российский префикс `8` в 11-значном номере заменяется на `7`. Найденный через `CheckAccount` `chatId` используется и для отправки, и для сопоставления входящих сообщений. Это важно для MAX: внутренний ID пользователя отличается от телефонного номера. Доступность поиска зависит от настроек приватности получателя и ограничений MAX.

## Что реализовано

- React + TypeScript, Vite и обычный CSS, иконки Lucide.
- Экран подключения с проверкой состояния инстанса и переключателем видимости токена.
- Создание личного чата по телефону через `CheckAccount`, повторное открытие уже существующего чата.
- Минимальный интерфейс по образцу веб-чата MAX: навигация, список диалогов, сообщения, поле ввода; голубая палитра, аватары и округлённые пузыри.
- Поиск по имени/телефону, непрочитанные сообщения, даты и время, черновик для каждого чата в памяти текущего подключения.
- Отправка текста до 4000 символов методом `SendMessage`. Enter отправляет, Shift+Enter переносит строку; IME-ввод не отправляет сообщение преждевременно.
- Входящие `textMessage` и `extendedTextMessage` (в том числе текст со ссылкой).
- Последовательный long polling через `ReceiveNotification` с `receiveTimeout=30`, подтверждение `DeleteNotification` после обработки.
- История текстовых сообщений в `sessionStorage`, отдельно для адреса API и инстанса. Сохранение выполняется **до** подтверждения уведомления. Повторные уведомления отсекаются по `idMessage`.
- Отмена запросов при выходе/закрытии формы, пауза при постоянных ошибках, автоматическое переподключение с увеличением задержки при сетевых ошибках/429/5xx.
- Статусы исходящих при включённом `outgoingWebhook`: принятие API, доставка, прочтение, ошибка. Принятие API само по себе не означает доставку.
- Явные ошибки и ручной повтор отклонённых сообщений. При таймауте/сетевой ошибке статус помечается как неизвестный, без автоматической повторной отправки.
- Мобильная версия: список и переписка открываются отдельными экранами с кнопкой возврата.
- Демо без учётных данных и без запросов к API.

Файлы, реакции, группы как отдельная функция, загрузка старой переписки, контакты, регистрация и звонки не входят в задание. Нетекстовые уведомления и эхо исходящих подтверждаются и пропускаются; сообщения с другого устройства не импортируются в историю. Входящий текст из ранее неизвестного чата создаёт диалог автоматически.

## Методы API

Базовый путь: `{apiUrl}/waInstance{idInstance}`. Современный MAX API допускает вызовы без `/v3`; если скопированный `apiUrl` уже содержит `/v3`, такой вариант тоже поддерживается.

| Назначение | Метод | Путь после базового | Данные |
| --- | --- | --- | --- |
| Состояние инстанса | GET | `/getStateInstance/{token}` | — |
| Поиск MAX-пользователя | POST | `/checkAccount/{token}` | `{ "phoneNumber": 79991234567 }` |
| Отправка текста | POST | `/sendMessage/{token}` | `{ "chatId": "<ID из checkAccount>", "message": "Привет!" }` |
| Получение уведомления | GET | `/receiveNotification/{token}?receiveTimeout=30` | — |
| Подтверждение обработки | DELETE | `/deleteNotification/{token}/{receiptId}` | — |

Проверка номера выполняется только при явном создании нового чата, без перебора номеров и автоматического повтора `CheckAccount`.

## Команды и сборка

```sh
npm run dev        # Локальная разработка: 127.0.0.1:5173
npm run typecheck  # Статическая проверка TypeScript
npm run build      # TypeScript + production-сборка в dist/
npm run preview    # Предпросмотр сборки: 127.0.0.1:4173
```

Lock-файл включён в проект; используй `npm ci` для повторяемой установки. Порты фиксированы: если порт занят, останови занявший его процесс или передай Vite другой порт.

Содержимое `dist/` можно выложить на любой статический HTTPS-хостинг. `base: './'` позволяет размещать приложение и в подкаталоге. Клиентской маршрутизации нет, серверные rewrite-правила не нужны. Веб-хостинг настраивается отдельно от публикации исходников в GitHub; отправка письма работодателю не автоматизирована.

## Данные и ограничения

Токен хранится только в замыкании API-клиента текущего подключения и не записывается в `localStorage`, `sessionStorage`, `.env` или логи. После обновления страницы или выхода его нужно ввести заново. Выход из интерфейса не вызывает `logout` GREEN-API и не отключает MAX на стороне сервиса.

В `sessionStorage` сохраняются номера, имена и тексты переписки. История доступна после обновления и повторного входа в той же вкладке, но не является серверным архивом. При закрытии вкладки браузер обычно очищает её; восстановление закрытой вкладки может восстановить и историю. Для удаления вручную очисти ключи с префиксом `max-green-chat:` в DevTools → Application → Session Storage. Экран восстановления также предлагает очистить только историю этого приложения в текущей вкладке. Демо ничего не сохраняет между подключениями.

Входящая очередь сервиса хранится ограниченное время (по документации — 24 часа). Подтверждённые события повторно из очереди не загрузятся. Полноценная долговременная история потребовала бы отдельного серверного хранилища. Если `sessionStorage` заблокирован или заполнен, получение приостанавливается без подтверждения несохранённого текстового уведомления.

Это клиентское тестовое задание: токен неизбежно доступен в памяти и в Network браузера, а по протоколу GREEN-API входит в URL запроса. Адреса API ограничены HTTPS-доменами `green-api.com`; произвольный сервер с формы получить токен не может. Сырые ошибки API не выводятся, так как они могут содержать URL с токеном. Для многопользовательского production-продукта стоит вынести секреты и обмен с API на сервер.

Прямые запросы из браузера зависят от CORS на стороне GREEN-API. Если сервис запрещает origin, понадобится собственный backend/proxy с конкретным разрешённым адресом API. Публичные CORS-прокси не используются. У текущей реализации нет попыток обойти настройки сервиса.

## Проверка после добавления токена

Интеграционные проверки с реальным MAX-аккаунтом в эту поставку не входят. Короткий сценарий для ручной проверки:

1. Открыть демо, переключить диалог, отправить локальное сообщение, проверить мобильную ширину.
2. Подключить свой авторизованный MAX-инстанс; проверить ошибку неверных учётных данных.
3. Добавить известный MAX-номер, отправить текст и получить ответ с другого аккаунта.
4. Ответить в два разных диалога, проверить непрочитанные и сопоставление по `chatId`.
5. Обновить страницу, войти с теми же данными, убедиться, что история этой вкладки восстановилась.
6. Отключить сеть, затем восстановить её; проверить переподключение. При таймауте отправки сначала проверить доставку в MAX.
7. Выйти: запросы должны отмениться, интерфейс должен вернуться к форме подключения.
